# Интеграция с агентом (MCP)

Статус: 2026-10-24, реализован начальный срез. Протокол, инструменты и транзакции проверены тестами с настоящим SQLite, поддельным Telegram и HTTP-клиентом MCP. В тот же день бот запущен на сервере с живым Telegram, а сессия Claude Code подключена к hoarder через SSH-мост и к Knuspr. Проверены только чтение и подключение; корзина ещё не собиралась, доставки не учитывались.

## Зачем

Внешний агент (сессия Claude Code или другой MCP-клиент) собирает корзину в интернет-магазине по рекомендациям hoarder и после доставки сообщает, что привезли. hoarder остаётся без LLM: он отдаёт прогноз каждого предмета и принимает точные факты. Агент сопоставляет предметы с товарами магазина, учитывает то, чего hoarder не отслеживает (продукты, разовые покупки), и пишет сводку владельцу.

Границы не меняются:

- рекомендация — не заказ; hoarder и агент не оформляют и не оплачивают заказы, это делает владелец в магазине;
- каждый предмет считается отдельно; ответ `shopping_needs` для предмета не зависит от других предметов;
- доставка — это точное добавление количества в момент доставки, ровно один раз на заказ, без сброса к цели;
- резерв и настройки предметов агент не меняет.

## Включение

MCP выключен, пока не задан адрес. Эндпоинт работает в том же процессе, что и бот, — с той же единственной SQLite-базой. Слушать можно только loopback; удалённому агенту нужен SSH-туннель или TLS-прокси с аутентификацией.

| Переменная | Значение |
|---|---|
| `HOARDER_MCP_ADDR` | `127.0.0.1:8765`, `[::1]:8765` или `localhost:8765`; пусто — MCP выключен |
| `HOARDER_MCP_TOKEN_FILE` или `HOARDER_MCP_TOKEN` | Bearer-токен, не короче 32 символов; ровно один источник |

```sh
umask 077
openssl rand -hex 32 > /absolute/private/path/mcp-token
export HOARDER_MCP_ADDR='127.0.0.1:8765'
export HOARDER_MCP_TOKEN_FILE='/absolute/private/path/mcp-token'
```

Адрес эндпоинта: `http://127.0.0.1:8765/mcp`. Неверный адрес или занятый порт останавливают запуск бота; сбой MCP после запуска только пишется в лог и не останавливает опросы.

Транспорт — Streamable HTTP, только `POST` с JSON-ответами: без SSE-потока, сессий и пакетных запросов. Версии протокола: `2025-11-25`, `2025-06-18`, `2025-03-26`. Запросы с заголовком `Origin` (браузеры) отклоняются.

## Инструменты

| Инструмент | Что делает |
|---|---|
| `shopping_needs` | Прогноз каждого активного предмета сейчас и к моменту `until` (или через `horizon_days`, до 60 дней). `needed_by_until` — то же правило, что у `/shopping`, но на заданный момент. `min_units_to_cover` — наименьшее целое число единиц, после которого предмет к этому моменту уже не рекомендуется; это минимум, а не целевой запас. Для каждого предмета — его связи с товарами магазина |
| `set_shop_link` | Связь предмета с товаром Knuspr: `product_id`, `product_name`, `units_per_pack` (сколько единиц предмета в одной упаковке магазина), необязательная заметка о заменах |
| `remove_shop_link` | Удаляет связь |
| `record_delivery` | Учитывает доставленный заказ: по строке на предмет, `units` в единицах предмета или `packs` через связь |
| `request_checks` | Сразу отправляет владельцу вопросы о текущем остатке до 10 предметов |
| `notify_owner` | Отправляет владельцу короткое сообщение, например сводку корзины |

Единица у каждого предмета своя — стандартная упаковка. Остатки и расход — эвристические интервалы `[low, high]`, а не откалиброванные вероятности. Приостановленные предметы `shopping_needs` возвращает только с `include_paused`, архивные — никогда.

## Доставки

ID события — `delivery:<shop>:<order_id>`, поэтому повтор того же вызова ничего не меняет (`already_recorded`), а тот же заказ с другим количеством или временем отклоняется. `delivered_at` — фактическое время доставки из заказа, не время вызова; будущее время отклоняется.

Если после `delivered_at` у предмета уже есть более новое наблюдение или изменение настроек, строка отклоняется. Более поздняя проверка уже включает привезённые упаковки, и добавление посчитало бы их дважды. В этом случае агент должен попросить владельца проверить предмет (`request_checks`).

После учёта пересчитывается план только этого предмета, рекомендация закрывается, если больше не нужна, открытый вопрос по предмету устаревает. Базовая модель не обучает темп расхода на интервалах с пополнениями; точные доставки сохраняют правильный остаток и пригодятся будущей модели.

## Сообщения вне общего часа

`request_checks` и `notify_owner` — явное исключение из правила «автоматические сообщения только в общий час»: их инициирует агент, которого настроил владелец. `notify_owner` ограничен 10 сообщениями в локальные сутки. Сообщения уходят при ближайшей отправке очереди — обычно в течение 30 секунд из-за long polling Telegram. Ответы на `request_checks` — обычные наблюдения; сам запрос наблюдением не является.

## Подключение агента

Эндпоинт слушает только loopback сервера. Удалённому клиенту не нужны ни туннель, ни копия токена: [deploy/mcp-stdio.py](../deploy/mcp-stdio.py) на сервере переводит MCP stdio в запросы к эндпоинту и сам читает токен из файла. Клиент запускает мост по SSH, и токен не покидает сервер:

```sh
ssh -o BatchMode=yes user@server python3 bots/hoarder/deploy/mcp-stdio.py
```

### Claude Code

MCP-серверы из `.mcp.json` видны только сессиям, открытым в папке этого файла. Поэтому для агента заводится отдельная папка, например `knuspr-agent`, с `.mcp.json`:

```json
{
  "mcpServers": {
    "hoarder": {
      "type": "stdio",
      "command": "ssh",
      "args": ["-o", "BatchMode=yes", "user@server", "python3", "bots/hoarder/deploy/mcp-stdio.py"]
    },
    "knuspr": { "type": "http", "url": "https://mcp.knuspr.de/mcp" }
  }
}
```

В `.claude/settings.local.json` той же папки `"enabledMcpjsonServers": ["hoarder", "knuspr"]` снимает запрос на одобрение, а `permissions.deny` закрывает опасные инструменты Knuspr (ниже). В Knuspr входит владелец, командой `/mcp` в сессии агента. Правила агента — в `CLAUDE.md` этой папки. Другие сессии Claude Code обращаются к сессии агента как к прокси: отправляют ей запросы и получают ответы, не подключая MCP у себя.

### Что запретить в Knuspr

MCP Knuspr (на 2026-10-24 у него 58 инструментов) умеет не только работать с корзиной. Инструмента отправки заказа у него нет: оформление завершает владелец по ссылке `get_checkout_link`. Но есть изменение оформления (слот, адрес, упаковка, способ оплаты, подзаказ), резервирование слотов, отмена заказа и удаление позиций из него, обращения и оценки, учёт тары, задачи по расписанию, `clear_cart` и `delete_shopping_list`. Клиент агента должен запретить их правилами доступа: граница «агент не заказывает» не может держаться только на инструкции модели.

Агенту разрешены чтение (`get_*`, `fetch_orders`, `analyze_spending`, `batch_search_products`, `search_*`) и точечные правки корзины и списков покупок. Список запрета не закрывает инструменты, которые Knuspr добавит позже. Поэтому правила агента требуют спрашивать владельца о любом инструменте вне разрешённого списка, а список нужно сверять при обновлениях Knuspr.

### Другие клиенты

Любой stdio-клиент подключается тем же мостом, например Codex: `codex mcp add hoarder -- ssh -o BatchMode=yes user@server python3 bots/hoarder/deploy/mcp-stdio.py`. Инструменты Knuspr в Codex ограничивает `enabled_tools` в `[mcp_servers.knuspr]`. Этот вариант не проверялся.

## Сценарий сборки корзины

hoarder ведёт только вещи длительного пользования — непортящиеся расходники. Продукты в нём не моделируются: агент набирает их по истории заказов магазина (`get_typical_order`, прошлые заказы, избранное, списки покупок), и владелец их подтверждает. Поэтому корзина состоит из двух независимых частей.

1. `shopping_needs` с `until` — время доставки после следующей, чтобы не покупать впритык.
2. Для предметов без связи найти товар в Knuspr, предложить владельцу и сохранить `set_shop_link`.
3. Для неуверенных предметов (нет обучающих интервалов, широкий интервал) — `request_checks` до покупки.
4. Положить в корзину `min_units_to_cover`, пересчитанный в упаковки магазина.
5. Отдельно предложить продукты по прошлым заказам и добавить подтверждённые.
6. Проверить наличие и замены. `notify_owner`: что добавлено (по предметам hoarder и по продуктам), чего нет и чем заменено, что под вопросом, сумма, минимальный заказ, ссылка на оформление.
7. После доставки — `record_delivery` по заказу из истории Knuspr, только для предметов hoarder.

## Ограничения

Одна связь на предмет и магазин; поддерживается только `knuspr`. Нет истории связей, отмены доставки и исправления ошибочного количества — нужна будущая команда исправления, а не правка событий. Старые записи `agent_notice` не очищаются. Межпроцессной аренды нет: MCP работает только внутри единственного процесса бота.
