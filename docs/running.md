# Запуск и эксплуатация первой версии

Это запускаемый Telegram-бот с SQLite и inline-кнопками. Интеграционные тесты используют настоящий HTTP-клиент и SQLite, но поддельный Telegram API. Проверки с живым ботом, серверное развёртывание и домашний пилот не проводились.

## Сборка

Нужны Go и C-компилятор: SQLite-драйвер `github.com/mattn/go-sqlite3` использует CGO. CI проверяет Linux amd64 на Go 1.27.1. Директива `go 1.23.0` — совместимость языка, а не рекомендация использовать старую версию для сетевого сервиса.

```sh
git clone https://github.com/EugenSleptsov/hoarder.git
cd hoarder
make check
mkdir -p bin
CGO_ENABLED=1 go build -o bin/hoarder ./cmd/hoarder
./bin/hoarder -h
```

Офлайн-сценарий ядра остался доступен: `go run ./cmd/hoarder-sim`. Он не обращается к Telegram и не доказывает точность бытового прогноза.

## Конфигурация

Бот рассчитан на один заранее разрешённый личный чат и один процесс на базу/токен. Групповые чаты и несколько членов семьи пока не поддерживаются. `HOARDER_CHAT_ID` — положительный числовой ID владельца личного чата, не username. База сохраняет владельца и откажется открываться под другим ID.

Храните токен в отдельном файле вне Git, доступном только владельцу процесса, например с правами `0600`. Не помещайте токен в README, команды Git, сообщения об ошибках или issue. Вместо файла можно задать `TELEGRAM_BOT_TOKEN`, но одновременно два источника запрещены. Не передавайте токен в аргументах процесса.

```sh
export HOARDER_CHAT_ID='YOUR_NUMERIC_PRIVATE_CHAT_ID'
export TELEGRAM_BOT_TOKEN_FILE='/absolute/private/path/telegram-token'
export HOARDER_DB='/absolute/private/path/hoarder.db'
export HOARDER_TIMEZONE='Europe/Berlin'
export HOARDER_POLL_TIME='21:00'
export HOARDER_CATCH_UP='30m'

./bin/hoarder
```

Замените пути и ID своими значениями; файл токена должен уже существовать. После запуска отправьте боту `/start` из разрешённого личного чата.

| Переменная | Значение по умолчанию |
|---|---|
| `HOARDER_CHAT_ID` | Обязательна |
| `TELEGRAM_BOT_TOKEN_FILE` или `TELEGRAM_BOT_TOKEN` | Обязателен ровно один источник |
| `HOARDER_DB` | `data/hoarder.db` |
| `HOARDER_TIMEZONE` | `Europe/Berlin` |
| `HOARDER_POLL_TIME` | `21:00`, строго `HH:MM` |
| `HOARDER_CATCH_UP` | `30m`; допускается от `1m` до `4h` |

На существующей базе изменение временной зоны, часа или окна восстановления сейчас отклоняется. Это защита уже сохранённых дат предметов. Команда явного перепланирования ещё не реализована; не удаляйте базу ради смены часа.

## Что нажимать

`/start` и `/items` открывают реестр. Кнопка «Добавить предмет» просит название текстом; затем свойство резерва, начальная длительность упаковки, число закрытых упаковок и остаток открытой выбираются кнопками. Допустим также `/add Паста`.

`/today` открывает предметы с наступившей датой проверки, `/shopping` — рекомендации пополнить. `/cancel` отменяет ожидание названия; внутри диалога используйте кнопку «Отмена».

Обычная проверка: выбрать предмет → число закрытых упаковок → остаток открытой → иногда уточнить, были ли пополнения. «Не знаю / не смотрел» не считается измерением. «Не использовали» требует отдельного подтверждения за весь дом и явно указанный интервал.

«Уже купили» ведёт к проверке текущего остатка, а не прибавляет упаковку в момент нажатия. Покупка могла произойти раньше. История с неизвестными пополнениями не используется для обучения темпа расхода.

Старые, повторные, чужие и недоступные сообщения не должны менять запас. Каждый допустимый ответ сохраняется транзакционно вместе с планом и очередью обновления сообщения. Если Telegram временно недоступен, уже сохранённый ответ не откатывается.

## Ежедневное окно

Каждый предмет хранит собственную назначенную дату. В общий час бот собирает все независимо наступившие вопросы в одно меню, при необходимости с несколькими страницами. Лимита числа предметов в день нет. Пустое меню автоматически не отправляется.

После запуска с небольшим опозданием допускается отправка в пределах `HOARDER_CATCH_UP`. Окно дополнительно ограничено текущей локальной датой: оно не продолжается через полночь. Если окно пропущено, вопросы сохраняются до следующего ежедневного окна. Команды и ответы пользователя обрабатываются вне этого окна тоже.

Неотвеченный вопрос не останавливает расход. Пока риск не снят, вопрос может повторяться в следующий день. Настраиваемое уменьшение частоты таких повторов — дальнейшая задача; его нельзя маскировать обнулением расхода или увеличением резерва.

## Резервное копирование и восстановление

Команда создаёт согласованный снимок SQLite через `VACUUM INTO`, а не копирует только основной файл при активном WAL. Требуются ID владельца и путь базы; токен для этой команды не нужен. Папка назначения должна существовать, файл назначения — ещё нет.

```sh
HOARDER_CHAT_ID='YOUR_NUMERIC_PRIVATE_CHAT_ID' \
HOARDER_DB='/absolute/private/path/hoarder.db' \
./bin/hoarder -backup /absolute/private/backups/hoarder-snapshot.db
```

Проверьте исходный путь перед запуском: обычное открытие отсутствующей базы создаёт новую базу. Готовый снимок храните вне репозитория и отдельно от рабочего диска. Автоматическое расписание копирования и ротация ещё не реализованы.

Для восстановления остановите рабочий процесс, сохраните прежнюю базу со всеми её сопутствующими файлами, затем скопируйте снимок **под новым именем**, например `hoarder-restored.db`, с правами `0600`. Укажите этот новый путь в `HOARDER_DB` и тот же ID владельца. Так старые `-wal`/`-shm` не смешаются с восстановленной базой. Не удаляйте WAL у работающей базы.

## Отказы и ограничения

Polling завершается с понятной ошибкой при неверном токене или конфликте webhook/другого polling-процесса. Бот не удаляет webhook и не сбрасывает очередь Telegram автоматически. Ошибки сети повторяются; ограничения частоты учитывают ответ `retry_after`. Межпроцессной аренды отправителя нет — запускать несколько копий нельзя.

Если Telegram принял самое первое `sendMessage`, но процесс завершился до сохранения `message_id`, возможен дубликат внешнего сообщения. Применение ответов остаётся защищённым от повторов; exactly-once доставка Telegram не заявляется.

Неисправимые ошибки отправки/редактирования `400`/`403` сохраняются в `failed_delivery` вместо бесконечного повтора. Для свежего меню доступна команда `/items`. Сохранённые события остаются в базе. HTTP health endpoint, отдельная панель ошибок, очистка старых receipts/screens и автоматическое исправление удалённых Telegram-сообщений пока отсутствуют.

Первая форма ввода поддерживает до трёх закрытых и одну открытую стандартную упаковку. Начальный срок покупки — три дня, максимальный промежуток физической проверки — 90 дней, резерв — одна упаковка либо ноль. Это фиксированные начальные настройки реализации, не выученные параметры. Изменение конфигурации предмета, удаление и пауза ещё не доступны через интерфейс.

Прогноз остаётся `interval-baseline-v1`: без обучения годовой сезонности, без откалиброванных вероятностей и без гарантии против произвольного скачка спроса. Автоматических заказов, платежей и медицинских гарантий наличия нет.
