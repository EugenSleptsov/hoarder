# Запуск, обновление и эксплуатация

Это запускаемый Telegram-бот с SQLite и inline-кнопками. Тесты используют настоящий HTTP-клиент и SQLite, но поддельный Telegram API. Живое подключение, серверное развёртывание и домашний пилот не проводились.

## Сборка

Нужны Go и C-компилятор: `github.com/mattn/go-sqlite3` использует CGO. CI проверяет Linux amd64 / Go 1.27.1. Директива `go 1.23.0` — совместимость языка, не рекомендация использовать старую версию для сетевого сервиса.

```sh
git clone https://github.com/EugenSleptsov/hoarder.git
cd hoarder
make check
mkdir -p bin
CGO_ENABLED=1 go build -o bin/hoarder ./cmd/hoarder
./bin/hoarder -h
```

Для существующей установки сначала прочитайте раздел обновления ниже. Офлайн-сценарий ядра: `go run ./cmd/hoarder-sim`.

## Конфигурация

Поддерживается один заранее разрешённый личный чат и один процесс на базу/токен. `HOARDER_CHAT_ID` — положительный числовой ID владельца личного чата, не username. База привязана к владельцу и не откроется под другим ID. Группы пока не поддерживаются.

Храните токен вне Git в отдельном файле с правами `0600`. Не передавайте его через аргументы процесса, сообщения в issue или команды Git. Допустим и `TELEGRAM_BOT_TOKEN`, но одновременно два источника запрещены.

```sh
export HOARDER_CHAT_ID='YOUR_NUMERIC_PRIVATE_CHAT_ID'
export TELEGRAM_BOT_TOKEN_FILE='/absolute/private/path/telegram-token'
export HOARDER_DB='/absolute/private/path/hoarder.db'
export HOARDER_TIMEZONE='Europe/Berlin'
export HOARDER_POLL_TIME='21:00'
export HOARDER_CATCH_UP='30m'
./bin/hoarder
```

Подставьте свои пути и ID. Файл токена должен уже существовать. После запуска отправьте `/start` из разрешённого чата.

| Переменная | По умолчанию |
|---|---|
| `HOARDER_CHAT_ID` | Обязательна |
| `TELEGRAM_BOT_TOKEN_FILE` или `TELEGRAM_BOT_TOKEN` | Обязателен ровно один источник |
| `HOARDER_DB` | `data/hoarder.db` |
| `HOARDER_TIMEZONE` | `Europe/Berlin` |
| `HOARDER_POLL_TIME` | `21:00`, строго `HH:MM` |
| `HOARDER_CATCH_UP` | `30m`, допустимо от `1m` до `4h` |

Изменение сохранённого общего часа, зоны или окна восстановления пока отклоняется. Нужна отдельная миграция расписания; не удаляйте базу ради смены часа. Индивидуальные настройки предметов редактируются через `/manage` независимо от этого ограничения.

## Обновление базы v1 → v2

**До первого открытия базы новым бинарником сделайте согласованную копию старым бинарником.** Даже команда `-backup` новой версии сначала открывает и мигрирует базу, поэтому для копии до миграции нужен прежний бинарник.

Порядок: остановить работающий процесс штатным сигналом; старым бинарником сделать backup по инструкции ниже; сохранить старый бинарник и снимок вне рабочей папки; обновить код через `git pull --ff-only`, проверить и собрать новый бинарник; запустить с прежними ID, путём и настройками расписания.

Открытие автоматически переводит схему v1 в v2 после проверки владельца. Таблицы остаются прежними, исторические JSON-события и хеши receipts не переписываются. Версия 2 нужна, чтобы старый код не игнорировал новые признаки паузы/архива и новые типы событий.

**Не понижайте `PRAGMA user_version` вручную.** Для отката остановите новую версию и используйте старый бинарник с отдельной копией снимка, сделанного до обновления. Ответы, принятые после снимка, в такой копии отсутствуют. Базу v2 продолжает открывать только код, который её понимает.

## Обычные диалоги

`/start` и `/items` открывают реестр. «Добавить предмет» просит название текстом; дальше — кнопки резерва, длительности упаковки, числа закрытых упаковок и остатка открытой. Есть `/add Название`; `/cancel` отменяет ожидание названия. Внутри диалога используйте «Отмена».

`/today` открывает наступившие вопросы, `/shopping` — рекомендации активных предметов. «Уже купили» уточняет текущий остаток, а не добавляет упаковку в момент нажатия. При неизвестной истории пополнений темп расхода не обучается по этому интервалу.

«Не знаю / не смотрел» не считается измерением. «Не использовали» требует подтверждения за весь дом и указанный интервал. Частичный ответ о закрытых упаковках не комбинируется с намного более поздней проверкой открытой упаковки.

## Управление кнопками

`/manage` или «Управление предметами» → предмет → «Настройки», «Приостановить опросы», «Возобновить опросы», «Убрать в архив».

Пауза выключает автоматические вопросы и скрывает рекомендацию из `/shopping`. Расход продолжает прогнозироваться. Дата проверки сохраняется, даже если просрочена. После возобновления она снова участвует в обычном ежедневном опросе; вне окна самостоятельного уведомления нет. Проверить остаток вручную можно и на паузе, это не включает уведомления.

Настройки предлагают резерв 0/1 упаковка, время на покупку 1/3/7/14 дней и максимальный интервал проверки 7/30/90/180 дней. Следующий экран показывает старое и новое значение и просит подтверждение. Меняются только настройки, план и рекомендация этого предмета — не физический запас. Повторное сохранение прежнего значения оставляет дату и ревизию без изменений.

Архивирование требует подтверждения. Предмет скрывается из обычного реестра, вопросов и списка покупок, история остаётся. `/archive` → предмет → «Восстановить на паузе». Для включения вопросов затем нажмите «Возобновить опросы». Архив не удаляет историю из базы, backups и Telegram. Переименование и изменение единицы упаковки ещё не поддерживаются.

Старые кнопки проверяются по версии экрана, ревизии предмета, владельцу и исходному сообщению. Незавершённый вопрос устаревает после изменения настроек/паузы/архивирования. Изменения сохраняются транзакционно раньше внешнего обновления сообщения.

## Ежедневное окно и отправки

Каждый предмет хранит собственную дату. В общий час бот собирает все активные наступившие вопросы в одно меню со страницами. Лимита предметов в день нет; пустое меню не отправляется.

При небольшом опоздании доставка допускается в пределах `HOARDER_CATCH_UP`, но только до конца текущей локальной даты. После пропуска окна вопросы сохраняются до следующего окна. Пользовательские команды и ответы доступны вне этого времени.

Перед отправкой очередного автоматического меню список проверяется снова. Предмет, поставленный на паузу после подготовки меню, отфильтровывается; пустое меню отменяется. Если отправка уже началась, SQLite не может атомарно отменить сетевой запрос. Устаревшая кнопка всё равно не должна менять данные.

Неотвеченные вопросы не останавливают расход и могут повторяться на следующий день. Настраиваемое уменьшение частоты повторов пока не реализовано. Оно не должно маскироваться увеличением запаса или нулевым расходом.

## Резервное копирование и восстановление

`-backup` создаёт согласованный снимок через SQLite `VACUUM INTO`, а не копирует только основной файл при активном WAL. Нужны ID владельца и путь базы, но не токен. Папка назначения должна существовать, файл — ещё нет.

```sh
HOARDER_CHAT_ID='YOUR_NUMERIC_PRIVATE_CHAT_ID' \
HOARDER_DB='/absolute/private/path/hoarder.db' \
./bin/hoarder -backup /absolute/private/backups/hoarder-snapshot.db
```

Проверьте исходный путь: обычное открытие отсутствующей базы создаёт новую базу. Для снимка до обновления используйте старый бинарник. Храните снимок вне Git и отдельно от рабочего диска. Автоматического расписания/ротации копий нет.

Для восстановления остановите процесс, сохраните старую базу и сопутствующие файлы, скопируйте backup **под новым именем** с правами `0600`, затем укажите этот путь в `HOARDER_DB` и прежний ID владельца. Так старые `-wal`/`-shm` не смешаются с восстановленным снимком. Не удаляйте WAL у работающей базы.

## Отказы и ограничения

Polling явно завершается при неверном токене или конфликте webhook/другого polling-процесса. Webhook не удаляется и очередь Telegram не сбрасывается автоматически. Сетевые ошибки повторяются; учитывается `retry_after`. Межпроцессной аренды отправителя нет — несколько копий запускать нельзя.

Если Telegram принял первый `sendMessage`, но процесс завершился до сохранения `message_id`, возможен дубликат. Exactly-once доставка не заявляется. Неисправимые `400`/`403` сохраняются в `failed_delivery`; свежее меню доступно через `/items`. Нет отдельной панели ошибок, health endpoint, очистки старых служебных записей и автоматического восстановления удалённых сообщений.

Ввод поддерживает до трёх закрытых и одну открытую стандартную упаковку. Прогноз остаётся `interval-baseline-v1`: без обучения сезонности, откалиброванных вероятностей и гарантии против произвольного скачка спроса. Автоматических заказов, платежей и медицинских гарантий нет.
